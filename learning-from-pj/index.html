How to use this guide

1. Authentication & Sessions

Authentication is more than a login screen. It's about state — who is the user, where do they belong, what happens when something goes wrong mid-flow.

Restoring sessions on app startup

lib/main.dart

🚫 The Mistake

return MaterialApp(
  title: 'Food App',
  initialRoute: '/',  // always WelcomeScreen, even if logged in
  routes: AppRoutes.getRoutes(),
);

Why It Matters

Firebase Auth automatically persists the user's session to disk. When the app restarts, the user is still authenticated — but your app doesn't know that and forces them back to the welcome screen. Users will think they got logged out, which feels broken.

✅ The Fix

final initialRoute = FirebaseAuth.instance.currentUser != null
    ? AppRoutes.mainRoute
    : AppRoutes.initialRoute;

return MaterialApp(
  initialRoute: initialRoute,
  routes: AppRoutes.getRoutes(),
);
Takeaway: Every authenticated app needs a startup decision based on existing auth state. Don't assume new launch = new session.

Protecting routes that need authentication

lib/screens/main_screen.dart

🚫 The Mistake

class _MainScreenState extends State<MainScreen> {
  int _selectedScreenIndex = 0;

  // no check that the user is logged in!
  // any code can navigate to /main and bypass auth
}

Why It Matters

If anything pushes /main while no Firebase user is signed in, every screen inside will try to call AuthService.getToken() and crash. Routes that require auth must protect themselves — don't trust the caller.

✅ The Fix

@override
void initState() {
  super.initState();
  if (FirebaseAuth.instance.currentUser == null) {
    WidgetsBinding.instance.addPostFrameCallback((_) {
      if (mounted) {
        Navigator.pushNamedAndRemoveUntil(
          context,
          AppRoutes.initialRoute,
          (_) => false,
        );
      }
    });
  }
}
Takeaway: Route protection is the route's responsibility. The caller might forget — the screen itself never should.

Two-system writes need a rollback plan

lib/services/auth_service.dart — register()

🚫 The Mistake

final credential = await _auth.createUserWithEmailAndPassword(...);
await credential.user?.updateDisplayName(name);

final response = await http.post('$_baseUrl/auth/register', ...);

if (response.statusCode != 201) {
  throw Exception('Registration failed');
  // Firebase account exists, backend has nothing — user is stuck!
}

Why It Matters

You're writing to two systems: Firebase Auth (creates the account) and your PostgreSQL backend (stores the profile). If the second one fails, the first one already succeeded. Now the user can "log in" with Firebase but your backend has no record of them — they're in a broken half-state with no way to retry.

✅ The Fix

if (response.statusCode == 201) {
  return jsonDecode(response.body);
}

// Backend rejected — roll back the Firebase account so
// the user can retry cleanly.
try {
  await user.delete();
} catch (_) {}

throw Exception('Registration failed');
Takeaway: When operation A depends on operation B succeeding, plan the rollback for A if B fails. This pattern is called a compensating action.

Graceful degradation when one service is down

lib/services/auth_service.dart — login()

🚫 The Mistake

await _auth.signInWithEmailAndPassword(...);  // success
final response = await http.get('$_baseUrl/auth/me', ...);

if (response.statusCode == 200) {
  return jsonDecode(response.body);
}
throw Exception('Login failed');
// Firebase says "you're logged in", but app shows error.
// User can't get past the login screen even with correct password.

Why It Matters

Your authentication source of truth is Firebase. The backend's /auth/me is a nice-to-have (extra profile data), not the gatekeeper. If your backend is briefly down, users with valid credentials still shouldn't be locked out.

✅ The Fix

final credential = await _auth.signInWithEmailAndPassword(...);
final user = credential.user;

final fallback = {
  'id': user?.uid,
  'name': user?.displayName,
  'email': user?.email,
};

try {
  final response = await http
      .get('$_baseUrl/auth/me', ...)
      .timeout(const Duration(seconds: 10));
  if (response.statusCode == 200) return jsonDecode(response.body);
  return fallback;
} on TimeoutException { return fallback; }
on SocketException { return fallback; }
Takeaway: Identify your source of truth for each domain (auth = Firebase). When auxiliary services fail, degrade gracefully instead of blocking the user.

2. Async UI State

Most app crashes and "weird behavior" come from async code. Networks fail. Users tap buttons twice. Things take longer than expected. Plan for it.

Always set a timeout on network calls

lib/services/auth_service.dart, lib/screens/auth/onboarding_screen.dart

🚫 The Mistake

final response = await http.get(Uri.parse('$_baseUrl/auth/me'), ...);
// no timeout — if server hangs, this hangs forever

Why It Matters

If the server is slow, unreachable, or the user is on bad WiFi, your await never returns. The login spinner spins forever. The user can't dismiss it. They force-quit the app.

✅ The Fix

final response = await http
    .get(Uri.parse('$_baseUrl/auth/me'), ...)
    .timeout(const Duration(seconds: 10));
Takeaway: Networks fail. Always set a budget. Pair every await http.X(...) with .timeout(...).

Always check the HTTP response

lib/screens/auth/onboarding_screen.dart — _finishOnboarding()

🚫 The Mistake

await http.post(
  Uri.parse('$_baseUrl/users/body-metrics'),
  body: jsonEncode(metrics.toMap()),
);

if (mounted) {
  Navigator.pushReplacementNamed(context, '/main');
}
// Response is ignored. User goes to main screen even if save failed.

Why It Matters

Every network call has three outcomes: success (2xx), server-rejected (4xx/5xx), or no response (timeout/network error). If you don't handle each, failures become invisible — the user thinks their data was saved, but it wasn't.

✅ The Fix

try {
  final response = await http
      .post(...)
      .timeout(const Duration(seconds: 10));

  if (response.statusCode != 200 && response.statusCode != 201) {
    ScaffoldMessenger.of(context).showSnackBar(
      SnackBar(content: Text('Failed to save (${response.statusCode}).')),
    );
    return;
  }
  Navigator.pushReplacementNamed(context, '/main');
} catch (e) {
  ScaffoldMessenger.of(context).showSnackBar(
    const SnackBar(content: Text('Connection error.')),
  );
}
Takeaway: Three outcomes for every network call. Handle all three. Silent failures are the worst kind of bug — users blame themselves.

Use a loading flag to prevent double submissions

lib/screens/auth/onboarding_screen.dart

🚫 The Mistake

ElevatedButton(
  onPressed: _nextPage,  // no busy state
  child: Text('Finish'),
)
// User taps "Finish" 3 times quickly → 3 POST requests fired.

Why It Matters

Async operations take time. While the first tap is in flight, the button is still active. Impatient users tap again. Your server gets duplicate writes — possibly creating duplicate records or worse, partial updates that overwrite each other.

✅ The Fix

bool _isSubmitting = false;

Future<void> _finishOnboarding() async {
  if (_isSubmitting) return;        // guard #1
  setState(() => _isSubmitting = true);
  try {
    await http.post(...);
  } finally {
    if (mounted) setState(() => _isSubmitting = false);
  }
}

ElevatedButton(
  onPressed: _isSubmitting ? null : _nextPage,  // guard #2
  child: _isSubmitting
      ? CircularProgressIndicator(...)
      : Text('Finish'),
)
Takeaway: Every async button needs three things: a busy flag, a disabled state, and a visual indicator. Always use try/finally to reset the flag.

3. Form Validation & UX

If you put a guard somewhere, make it the only path forward. Otherwise users will find the path you didn't guard.

Don't let users bypass your own validation

lib/screens/auth/onboarding_screen.dart

🚫 The Mistake

PageView(
  controller: _pageController,
  onPageChanged: onPageChanged,
  children: [_buildStep1(), _buildStep2(), _buildStep3()],
)
// "Next" button validates each step,
// but the user can swipe horizontally to skip!
// Then _selectedSex! crashes because it's null.

Why It Matters

You added validation in the Next button — but PageView defaults allow horizontal swipes that bypass that button entirely. Users land on the Goal step with no height/weight set, then your ! operators crash on null.

✅ The Fix

PageView(
  controller: _pageController,
  physics: const NeverScrollableScrollPhysics(),  // disable swipe
  onPageChanged: onPageChanged,
  children: [...],
)
Takeaway: If you put a guard somewhere (the Next button), make it the only path forward. Disable every other way through.

If you show a checkbox, it must mean something

lib/screens/auth/register_sheet.dart

🚫 The Mistake

Checkbox(value: _rememberMe, onChanged: ...),
Text('I agree to the Terms and Conditions'),

ElevatedButton(
  onPressed: () async {
    // validates name/email/password,
    // but never checks _rememberMe!
    await AuthService.register(...);
  },
  child: Text('Register'),
)

Why It Matters

The UI claims something the code doesn't enforce. Users think they agreed to terms; legally and ethically you're claiming the same. If the checkbox doesn't gate the action, don't show it.

✅ The Fix

if (!_rememberMe) {
  ScaffoldMessenger.of(context).showSnackBar(
    const SnackBar(content: Text(
      'Please agree to the Terms and Conditions to continue',
    )),
  );
  return;
}
await AuthService.register(...);
Takeaway: UI affordances are promises. Every button, checkbox, and input must do what it visually claims to do.

4. Defensive Coding

Default values exist. Edge cases happen. The math you copy-pasted from Wikipedia doesn't know about empty form fields.

Guard divide-by-zero in computed properties

lib/models/body_metrics.dart

🚫 The Mistake

final double heightCm;  // defaults to 0.0

double get bmi => weightKg / ((heightCm / 100) * (heightCm / 100));
// crashes / returns Infinity if heightCm == 0

Why It Matters

Your model has a default value of 0.0. The moment something constructs a BodyMetrics() without setting height (which the model itself allows!), reading bmi divides by zero. Dart returns Infinity rather than crashing — but that Infinity propagates into UI and looks like a bug to the user.

✅ The Fix

double get bmi {
  if (heightCm <= 0) return 0;
  final heightM = heightCm / 100;
  return weightKg / (heightM * heightM);
}
Takeaway: Any division by user-provided input needs a guard. Trace your defaults through every computed property.

Defaults must be safe, not just compilable

lib/models/body_metrics.dart

🚫 The Mistake

double get tdee {
  const multipliers = {
    ActivityLevel.sedentary: 1.2,
    ActivityLevel.lightlyActive: 1.375,
    // ...
  };
  return bmr * (multipliers[activityLevel] ?? 0);
  // Unknown activity → multiplier of 0 → TDEE of 0 calories
}

Why It Matters

The ?? 0 compiles cleanly and silences null warnings — but a TDEE of zero kilocalories is medically nonsensical. The fallback is technically valid but semantically wrong. If this number drives a calorie display, your user sees "Goal: 0 kcal."

✅ The Fix

return bmr * (multipliers[activityLevel] ?? 1.2);
// Fall back to sedentary — a sensible, safe default
Takeaway: When you write ?? defaultValue, ask: "If this fallback is what the user sees, does it make sense?" If not, pick a better default.

5. Code Organization

Duplication is the root of drift. When you copy-paste, ask "where should this live?"

Don't keep two models for the same thing

lib/models/user_profile.dart vs lib/models/body_metrics.dart

🚫 The Mistake

// user_profile.dart
class UserProfile {
  final Gender gender;          // enum: unknown, male, female
  double get bmi => ...
  double get bmr => ...
}

// body_metrics.dart  ← almost identical!
class BodyMetrics {
  final Sex sex;                // enum: unknown, male, female
  double get bmi => ...
  double get bmr => ...
}

Why It Matters

Two near-identical classes mean every change has to happen twice. You will forget. Bugs will appear in only one of them. Your reviewer will be confused about which is canonical. This kind of drift is one of the top sources of bugs in real codebases.

✅ The Fix

// Delete user_profile.dart entirely.
// Use BodyMetrics everywhere.
// One model, one source of truth.
Takeaway: If two classes describe the same real-world thing, they should be one class. Refactoring duplicates early prevents drift later.

Constants belong in one place

lib/services/auth_service.dart, lib/screens/auth/onboarding_screen.dart

🚫 The Mistake

// auth_service.dart
static const String _baseUrl = 'http://192.168.1.13:3000';

// onboarding_screen.dart  ← same value, different file
static const String _baseUrl = 'http://192.168.1.13:3000';

Why It Matters

When the server IP changes (and it will — production, staging, your laptop's WiFi changing), you have to remember every place this string lives. Miss one, and that screen silently calls a dead URL.

✅ The Fix

// lib/config/api_config.dart
class ApiConfig {
  static const String baseUrl = 'http://192.168.1.13:3000';
}

// elsewhere
import 'package:app1/config/api_config.dart';
Uri.parse('${ApiConfig.baseUrl}/auth/me');
Takeaway: If you ever copy-paste a constant, stop and extract it. The "rule of three" says by the third copy, you must extract — but starting at the first is even better.

6. State & Security Hygiene

Small mistakes here become big problems later when the app grows or ships to production.

Don't use static for instance UI state

lib/screens/auth/login_sheet.dart, register_sheet.dart

🚫 The Mistake

class _LoginSheetState extends State<LoginSheet> {
  static bool _rememberMe = false;  // ← static!
}

Why It Matters

static means "this variable belongs to the class, not the instance." It persists for the lifetime of the app. If a user opens the login sheet, checks the box, closes it, and reopens it — the box is still checked. State leaks across instances. This is rarely what you want for UI.

✅ The Fix

class _LoginSheetState extends State<LoginSheet> {
  bool _rememberMe = false;  // instance field
}
Takeaway: static is essentially a global variable scoped to a class. Use it only when you genuinely want shared state across all instances (constants, singletons). Never for UI checkboxes.

Never log tokens, even partially

lib/services/auth_service.dart

🚫 The Mistake

print('[AuthService] POSTing to $_baseUrl/auth/register '
      'with token: ${token?.substring(0, 20)}...');

Why It Matters

Logs end up in places you don't expect: ADB output that gets shared, crash analytics services, screenshots in bug reports, paste-bins on Slack. Even a partial token can give an attacker a foothold or be combined with other leaks. Treat tokens like passwords — never put them in plain log statements.

✅ The Fix

// Just remove the print entirely.
// For real apps, use a logger that scrubs sensitive fields.
Takeaway: Tokens, passwords, API keys, session IDs — none of these belong in print() or console.log(). Build the discipline early.
